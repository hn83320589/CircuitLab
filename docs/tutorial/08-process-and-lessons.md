# 第 8 章　開發流程與實戰教訓

> **本章目標**
>
> - 理解「先設計、再確認、才開發」的流程
> - 學會把專案切成可以獨立驗證的里程碑
> - 寫出說明「為什麼」的 commit message
> - 從十個真實的除錯故事中，學習發現問題、追查原因、修正的方法

前面各章展示的是「最後的結果」。但真實的開發過程並不是一路順利的。本章誠實地記錄這個專案的開發過程，包括犯過的錯誤。**能從錯誤中學到東西的前提，是先承認犯了錯。**

## 8.1 先設計，再確認，才開發

這個專案的第一步不是寫程式，而是寫一份設計文件（[`docs/architecture.md`](../architecture.md)），內容包括需求分析、架構、演算法選擇、測試計畫和里程碑，最後列出 8 個**需要客戶確認的決策**：

| #   | 待確認的議題                         | 建議方案                         |
| --- | ------------------------------------ | -------------------------------- |
| 1   | 電動勢相同、r = 0 的電池並聯怎麼處理 | 合併求解並平分電流               |
| 2   | 電壓計串聯怎麼判斷                   | 以求解結果做啟發式判定，只給警告 |
| 3   | 元件大小                             | 長度 2 格，以中點旋轉            |
| 4   | 性質測試工具                         | fast-check                       |
| 5   | 格式化工具                           | Prettier                         |
| 6   | 部署平台                             | GitHub Pages + GitHub Actions    |
| 7   | React 版本                           | 19                               |
| 8   | 範例數量                             | 10 個                            |

客戶回覆「照建議」之後，才開始寫程式。

**為什麼要這樣做？** 架構層級的決策一旦寫進程式，修改的成本會隨著時間急遽上升。例如「元件長度 2 格」如果開發到一半才改成 3 格，幾何、旋轉、範例、測試都要重寫（而且長度 3 無法以中點旋轉，見第 2.2 節）。在設計文件階段改，只需要改一行字。

> **教學提示**：注意清單裡每一項都附上了「建議方案」，而不是只問「你想怎麼做」。好的提問會降低對方的決策成本：客戶只需要回答「好」或「不好」，不需要自己研究每個選項。

## 8.2 里程碑：每一步都能編譯、能測試

整個專案切成 12 個里程碑（M0–M11），每個里程碑結束時都必須：能編譯、通過所有既有測試、包含新功能的測試、通過 lint，然後 commit。

| 里程碑 | 內容                     | Commit                                                        |
| ------ | ------------------------ | ------------------------------------------------------------- |
| M0     | 專案骨架、CI、設計文件   | `0e8e76d` chore: 建立專案骨架與系統設計文件                   |
| M1     | 高斯消去法               | `827b4f3` feat(solver): 部分樞軸高斯消去法                    |
| M1     | MNA 管線與教科書電路     | `80050ec` feat(solver): MNA 求解管線與教科書電路測試          |
| M2     | 電錶、0 Ω 電流、獨立電路 | `ad2b815` test(solver): 電錶、0 Ω 元件電流與獨立電路的測試    |
| M3     | 錯誤接法偵測             | `71470b5` feat(solver): 錯誤接法偵測與學生用說明              |
| M4     | 性質測試                 | `5643dac` test(solver): 1,000 個隨機合法電路的性質測試        |
| M5     | 編輯器 reducer 與歷史    | `68af65c` feat(editor): 編輯動作 reducer 與 Undo/Redo 歷史    |
| M6–M7  | SVG 編輯器與結果呈現     | `42c2e47` feat(ui): SVG 電路編輯器與結果呈現                  |
| M8     | 預測模式與範例           | `848845a` feat(teaching): 預測模式與 10 個內建範例            |
| M9     | 存檔、分享、PNG          | `64220fe` feat(io): JSON 存檔、分享連結與 PNG 匯出            |
| M10    | E2E 與效能量測           | `019d207` test(e2e): 200 元件效能量測、冒煙測試與 README 截圖 |
| M11    | README 與部署            | `0cc3343`、`26fd34e` docs                                     |
| 驗收   | 測試報告與修正           | `f84bb10`、`fe556b9`、`69eb0e9`、`7cebf20`                    |

觀察這個順序：**先做最難、最核心、最容易測試的部分（求解器），最後才做 UI。** 理由是：

- 求解器是風險最高的部分。如果演算法有根本性的問題，越早發現越好。
- 求解器是純函式，可以完全用單元測試驗證，不需要等 UI。
- UI 完成時，求解器已經有 42 個測試保護，UI 開發過程中不必擔心改壞它。

## 8.3 Commit message：寫「為什麼」

比較兩種 commit message：

```text
❌ 修改 linalg.ts
```

```text
✅ feat(solver): 部分樞軸高斯消去法

MNA 矩陣中理想電壓源的列對角線為 0，必須換列才能求解；
奇異判定採相對門檻，因為電導值可能從 1e-6 跨到 100。
遇到奇異矩陣回傳 { ok: false }，絕不產生 NaN/Infinity。
```

`git diff` 已經告訴你「改了什麼」。commit message 要回答的是 diff 回答不了的問題：**為什麼這樣改？為什麼不用別的方法？**半年後有人看到「相對門檻」，想改成固定門檻時，這段說明就能阻止一個錯誤。

本專案的 commit 格式是 `類型(範圍): 標題`，再加上一段說明：

| 類型    | 用途               |
| ------- | ------------------ |
| `feat`  | 新功能             |
| `fix`   | 修正錯誤           |
| `test`  | 新增或修改測試     |
| `docs`  | 文件               |
| `chore` | 雜務（設定、建置） |

## 8.4 十個真實的除錯故事

### 故事 1：最新版不一定能用

- **現象**：查詢套件版本時，TypeScript 最新版是 7.0。
- **追查**：查詢 typescript-eslint 的 peer dependencies，發現它只支援 `typescript < 6.1.0`。
- **處理**：鎖定 TypeScript 6.0.3，並在設計文件和 commit message 中記錄原因。
- **教訓**：安裝前查 peer dependencies。生態系中的工具需要時間跟上新版本。

### 故事 2：−0.000000000000000178 安培

- **現象**：懸空電阻的測試失敗：`expected -1.7763568394002506e-16 to be +0`。
- **追查**：懸空電阻的一端連在電路上，另一端是一個只有它自己的超節點。MNA 解出的兩端電位「幾乎」相等，差了一點點浮點誤差，電流就變成 −1.8 × 10⁻¹⁶ A。
- **思考**：有兩種修法。
  - A. 測試改用 `toBeCloseTo(0)`。
  - B. 剝葉子演算法已經**證明**這個元件不可能有電流，直接把電流設為 0。
- **處理**：選 B。電流在物理上就是 0，結果應該精確反映這個事實。這也讓「電壓計串聯」的判定（需要判斷「沒有電流」）更可靠。
- **教訓**：面對浮點誤差，先問「這個值在數學上應該是多少？」如果有更上層的資訊可以確定答案，就用那個資訊，而不是放寬容差。

### 故事 3：Undo 測試的快照比電路多一張

- **現象**：「60 步全部復原」的測試失敗，提示兩個電路不相等。
- **追查**：測試每執行一個動作，就推入一張快照。第 5 步是「把內電阻設成 0.0」，但電池的內電阻**預設就是 0**。reducer 正確地判斷「沒有變化」，不寫入歷史；測試卻照樣推入了一張快照，於是快照比歷史多一張。
- **處理**：修正測試，讓每一步都會真正改變電路。
- **教訓**：**測試也會有 bug。**測試失敗時，要先判斷是程式錯了還是測試錯了，不要直接改程式讓測試通過。這個案例中，reducer 的行為才是正確的。

### 故事 4：從來沒有紅過的測試

- **現象**：M2 的 8 個測試寫好後，一次全部通過。
- **原因**：這些功能在 M1 寫求解器時就已經實作了，測試是事後補的，違反了 TDD「先紅後綠」的順序。
- **處理**：故意把導線電流的正負號改反，確認有 3 個測試會失敗，再還原（第 7.5 節）。
- **教訓**：沒看過紅燈的測試，不能確定它有效。補救方法是變異檢查。同時要**誠實地記錄**這次偏離了流程，不要假裝一切都照規矩來。

### 故事 5：快得可疑的性質測試

- **現象**：6,000 個隨機電路的性質測試只花 0.84 秒。
- **疑問**：產生器是不是產生了很多空電路，或沒有電流的電路？
- **追查**：寫一段臨時程式統計 1,000 個樣本：58% 有電流，平均 26 個元件，會觸發各種警告。
- **處理**：確認產生器有代表性，刪掉臨時程式。
- **教訓**：測試通過時也要保持懷疑。性質測試的價值取決於產生器，要檢查它產生了什麼。

### 故事 6：同一分頁貼上分享連結，電路不會切換

這是唯一一個**到了使用者手上才可能遇到**的產品缺陷，是開發完成後的驗收測試才發現的。

- **現象**：驗收腳本先開啟 `/`，再前往 `/#c=…`（分享連結），結果畫面上的電路沒有變。
- **追查**：
  1. 先在 Node 中直接呼叫 `solve()`，確認求解器算出的結果是正確的，排除求解器的問題。
  2. 注意到兩個網址**只差在 `#` 後面**。瀏覽器對這種網址變化的處理是「同頁跳轉」，不會重新載入頁面。
  3. App 只在啟動時讀取一次網址中的電路，之後就不再看了。
- **影響**：老師如果已經開著 CircuitLab，再把分享連結貼到同一分頁的網址列，電路不會切換，可能以為連結壞了。
- **修正**（照 TDD 的順序）：
  1. 先寫一個 E2E 測試重現這個情境，確認它**失敗**。
  2. 讓 App 同時監聽 `hashchange` 事件。
  3. 處理兩個細節：載入新電路時結束預測模式；連續貼上多個連結時只套用最後一個（避免較慢的解碼結果蓋掉較新的）。
  4. 測試通過，部署後再到線上版驗證一次。
- **教訓**：
  - ADR-8 選擇「把電路放在 hash」時，沒有追問這個決定的**所有後果**。
  - 需求分析時只考慮了「開啟連結」，沒有列舉使用者「取得連結之後」所有可能的動作（新分頁、同分頁、重新整理、上一頁……）。
  - 驗收測試從使用者的角度出發，能發現開發者視角的盲點。

### 故事 7：Playwright 說 `<g>` 看不見

- **現象**：驗收腳本中，4 個錯誤接法的測試都在等待頁面載入時逾時（30 秒）。
- **追查**：共用的 `openCircuit()` 會等「最後一個元件」變成可見。這 4 個測試電路的最後一個元件都是導線。SVG 的 `<g>` 群組本身沒有外框，Playwright 判定它「不可見」，就一直等到逾時。而之前的效能測試能通過，只是因為它的最後一個元件**碰巧**是電阻。
- **處理**：改成只等元素出現在 DOM 中（`state: 'attached'`）。
- **教訓**：「一直都能通過」的程式碼，可能只是運氣好。共用的測試工具要用各種不同的輸入驗證。

### 故事 8：200 個元件，數出來只有 199 個

- **現象**：基準電路的測試失敗：`expected length 200 but got 199`。
- **追查**：11 × 10 的網格有 10 × 10 = 100 條水平邊、11 × 9 = 99 條垂直邊，共 199 條。其中一條被電池佔用，所以是 198 條加 1 個電池 = 199。
- **處理**：把電池移到網格外側，用兩條導線接進來。網格的 199 條邊都是元件，加上電池剛好 200 個，而且**不把導線算進去**。這比把導線也算成元件更嚴格。
- **教訓**：差一錯誤（off-by-one）是最常見的 bug 之一。當需求有模糊空間（「200 個元件」包不包括導線？）時，選擇比較嚴格的解讀。

### 故事 9：數字正確，但畫面不夠好

- **現象**：「串聯與並聯對照」範例中，燈泡亮度值分別是 0.48 和 0.71，數值上有差異。但截圖中，兩組燈泡看起來差不多黃。
- **原因**：亮度只影響填色的透明度，視覺上的差距不明顯。
- **處理**：讓光暈的半徑和透明度也隨亮度變化，填色從淡黃漸變到飽和的金黃。改完後，並聯燈泡的光暈明顯大一圈。
- **教訓**：自動化測試可以驗證「亮度值正確」，但驗證不了「學生看得出差異」。**和使用者體驗有關的需求，一定要實際看畫面。**同一次檢查中也發現字體太小，不適合投影，一併放大了。

### 故事 10：是程式錯了，還是測試腳本錯了？

開發過程中，瀏覽器測試腳本出現過好幾次「看起來像 bug」的結果，追查後都是腳本本身的問題：

| 現象                              | 原因                                                   |
| --------------------------------- | ------------------------------------------------------ |
| 腳本找不到 `e3` 的標籤            | 範例中 4 Ω 電阻的 id 是 `e4`，腳本寫錯了               |
| 「開啟存檔後，電流計讀數是空的」  | 讀檔是非同步的，腳本在讀檔完成前就去抓讀數了           |
| 「60 步復原後，復原按鈕仍可以按」 | 「載入範例」本身也是一步可以復原的編輯，這是正確的行為 |
| 「範例中所有流動點方向都一樣」    | 範例的導線剛好都順著電流方向畫，腳本的假設不成立       |

但故事 6 告訴我們，**最後一列的追查繼續下去，真的找到了產品缺陷**。

- **教訓**：測試失敗時，兩種可能都要認真考慮。不要直接假設「一定是腳本寫錯」，也不要直接假設「一定是程式有 bug」。每一次都要追查到確定的原因為止。

## 8.5 完成的定義（Definition of Done）

每個任務都要符合以下條件，才算完成：

- [ ] 測試已撰寫且通過
- [ ] 符合專案慣例
- [ ] 沒有 linter／formatter 警告
- [ ] commit message 清楚說明「為什麼」
- [ ] 沒有不附 issue 編號的 TODO
- [ ] 回報了這次做了什麼、**沒做什麼**、做了哪些決策

最後一項特別重要。「沒做什麼」常常被省略，但它能避免誤會。例如效能量測時，報告中明確寫了「本次沒有附上 Performance 面板截圖，因為題目接受自動化量測佐證」，驗收者就不會以為漏做了。

## 8.6 如果重來一次

回顧整個專案，有幾件事可以做得更好：

| 項目               | 這次的作法                 | 下次會怎麼做                                    |
| ------------------ | -------------------------- | ----------------------------------------------- |
| 分享連結的使用情境 | 只考慮「開啟連結」         | 需求分析時列舉「取得連結後」的所有動作          |
| E2E 驗收測試       | 開發完成後才寫             | 每完成一個和畫面有關的功能，就寫對應的 E2E 測試 |
| M2 的測試          | 事後補寫                   | 嚴格照 TDD 順序：先寫測試再寫功能               |
| 投影時的可讀性     | 第一版字太小，看截圖才發現 | 一開始就在投影解析度下檢查畫面                  |
| 元件大小           | 固定 2 格，小螢幕上偏小    | 加上縮放功能（第 9 章練習）                     |

## 本章重點

1. 架構決策在寫程式之前確認；提問時附上建議方案。
2. 里程碑要能獨立驗證；先做最核心、風險最高的部分。
3. commit message 寫「為什麼」，不寫「改了什麼」。
4. 測試會有 bug，程式也會有 bug。每一次失敗都要追查到確定的原因。
5. 自動化測試驗證不了使用者體驗，要實際看畫面。
6. 誠實記錄偏離流程的地方和犯過的錯，它們是最有價值的學習素材。

## 練習

1. **（里程碑）** 如果要新增「電流源」元件，請把工作切成 3–4 個里程碑，每個里程碑寫出「完成時要通過哪些測試」。
2. **（commit message）** 為故事 2 的修正寫一則 commit message，說明為什麼選擇方案 B 而不是方案 A。
3. **（除錯）** 故事 6 中，第一步是「在 Node 中直接呼叫 `solve()`」。這一步排除了什麼可能性？為什麼要先做這一步？
4. **（反思）** 從你自己的專案中，選一個你遇到過的 bug，用「現象 → 追查 → 原因 → 處理 → 教訓」的格式寫下來。
5. **（討論）** 故事 9 的問題，有沒有辦法用自動化測試抓到？如果有，你會怎麼設計？如果沒有，你會在開發流程中加入什麼步驟？
