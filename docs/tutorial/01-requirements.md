# 第 1 章　需求分析

> **本章目標**
>
> - 從一段客戶需求中辨識利害關係人與使用情境
> - 把需求分成功能需求、非功能需求、限制、假設
> - 把模糊的描述改寫成「可以驗證」的條件
> - 找出需求中隱含的難題與衝突
> - 建立需求追溯矩陣

## 1.1 從客戶的故事開始

需求文件的開頭是這樣寫的：

> 一位國中理化老師想要一個能在教室投影、讓學生自己動手接電路的網頁工具，現有的工具不是要付費、就是介面太複雜。老師上課常在同一張畫布上放兩組電路做對照，例如「串聯」與「並聯」各一組，讓學生比較燈泡亮度。

很多人讀需求時會直接跳到功能列表，但**這段背景故事其實藏了最重要的設計線索**。逐句拆解：

| 原文                     | 隱含的需求                                   | 影響的設計                                         |
| ------------------------ | -------------------------------------------- | -------------------------------------------------- |
| 「在教室投影」           | 字要大、對比要高；畫面要能縮放到投影機解析度 | 用 SVG 向量繪圖；淺色主題；結果標籤的字級          |
| 「學生自己動手」         | 操作要直覺；學生**一定會亂接**               | 錯誤接法不能讓畫面當掉；錯誤訊息要用學生聽得懂的話 |
| 「現有工具要付費」       | 免費、不需要帳號                             | 純前端、靜態部署，不需要後端或登入                 |
| 「介面太複雜」           | 功能要少而精                                 | 只有 7 種元件；不做示波器、交流電等進階功能        |
| 「同一張畫布放兩組電路」 | 兩組互不相連的電路要能各自正確求解           | 求解器必須支援多個獨立電路（第 6.4 節）            |
| 「比較燈泡亮度」         | 亮度要能**跨電路**比較                       | 燈泡亮度用絕對刻度，不能依畫面上最亮的燈泡做正規化 |

最後一列特別值得注意。如果只看功能列表「燈泡亮度依消耗功率變化」，很自然會把畫面上最亮的燈泡設成 100%，其他燈泡依比例顯示。但這樣一來，串聯組和並聯組並排時，兩組的「最亮燈泡」看起來會一樣亮，學生就比不出差異了。**背景故事告訴我們這個功能真正的用途，也因此決定了它該怎麼實作。**

## 1.2 利害關係人與使用情境

| 角色                   | 目標                 | 使用情境                             | 最在意的事                       |
| ---------------------- | -------------------- | ------------------------------------ | -------------------------------- |
| 老師（投影操作者）     | 上課示範、引導討論   | 快速載入範例、切換開關、使用預測模式 | 操作快、畫面清楚、不會當場出錯   |
| 學生（動手操作者）     | 自己接電路、驗證想法 | 自由放置元件、故意接錯看看會怎樣     | 好玩、看得懂結果、看得懂錯誤原因 |
| 學生（預測活動參與者） | 先猜再驗證           | 選擇「變亮／變暗／不變」後看結果     | 結果判定要正確                   |
| 驗收者                 | 確認交付品質         | 依驗收標準逐條檢查                   | 每一條都有證據                   |
| 維護者（未來的開發者） | 修改與擴充           | 閱讀程式碼、新增元件                 | 程式好懂、測試完整               |

> **教學提示**：初學者常常漏掉「驗收者」和「維護者」。這兩個角色不會直接操作產品，但他們的需求（可驗證、可維護）會大幅影響架構。第 3 章會看到，「可測試性」被排在所有設計決策的第一優先。

## 1.3 需求分類

需求文件的內容可以分成四類。分類的目的是：**不同類型的需求，驗證方式不同**。

### 功能需求（系統要「做什麼」）

| 編號 | 需求                                                         | 來源段落   |
| ---- | ------------------------------------------------------------ | ---------- |
| F1   | 在格點畫布上放置 7 種元件                                    | 電路編輯器 |
| F2   | 元件可以拖曳、旋轉 90°、刪除；端點吸附格點；同一格點視為相連 | 電路編輯器 |
| F3   | 點選元件可以修改數值                                         | 電路編輯器 |
| F4   | 以 MNA 建立方程組並自行實作線性求解                          | 電路求解   |
| F5   | 每次編輯、切換開關後立即重算                                 | 電路求解   |
| F6   | 顯示每個元件的電流（含方向）、電壓、功率                     | 結果顯示   |
| F7   | 導線上以流動的點表示電流方向與大小                           | 結果顯示   |
| F8   | 燈泡亮度依功率變化；電錶顯示讀數                             | 結果顯示   |
| F9   | 錯誤接法要標出元件，並用一句話說明原因                       | 錯誤接法   |
| F10  | 預測模式                                                     | 教學功能   |
| F11  | Undo／Redo 至少 50 步                                        | 教學功能   |
| F12  | JSON 存讀、分享連結、匯出 PNG                                | 儲存與分享 |
| F13  | 至少 8 個內建範例                                            | 教材範例   |

### 非功能需求（系統要「做得多好」）

| 編號 | 需求                                                   | 類型     |
| ---- | ------------------------------------------------------ | -------- |
| N1   | 任何接法都不可以讓畫面當掉，不可以顯示 NaN 或 Infinity | 強健性   |
| N2   | 教科書電路的相對誤差 < 0.1%                            | 正確性   |
| N3   | KCL 誤差 < 1e-9 A；功率守恆誤差 < 1e-6                 | 正確性   |
| N4   | 200 個元件時，改一個值到畫面更新 < 100 ms              | 效能     |
| N5   | 錯誤訊息要讓學生看得懂                                 | 易用性   |
| N6   | 測試至少 40 個，lint 沒有錯誤                          | 可維護性 |

### 限制（不能改變的條件）

- 純前端：React 18 以上、TypeScript strict、Vite。
- 不可使用電路模擬、線性代數、繪圖編輯器套件。
- 不需要後端、資料庫、Docker。
- 只需支援桌機 Chrome／Edge 的滑鼠操作；畫布固定 60 × 40 格。

### 假設（客戶替我們簡化的部分）

- 只處理直流穩態，不處理電容、電感與暫態。
- 所有元件都是線性的，燈泡電阻不隨溫度改變。
- 導線沒有電阻；開關閉合時視同導線，斷開時視同斷路。
- 數值顯示到小數點後 3 位。

> **討論**：「不可使用線性代數套件」是限制還是功能需求？它其實是一個**教學目的的限制**：客戶要確認開發者真的理解演算法。這類限制在業界少見，但在教學或競賽專案中很常見。理解限制背後的原因，才能判斷它的邊界。例如，測試工具 fast-check 不屬於線性代數套件，所以可以用。

## 1.4 把模糊的需求改寫成可以驗證的條件

需求分析最重要的技能是：**看到一句需求，馬上問「我要怎麼證明做到了？」**

| 原始描述              | 問題           | 改寫成可驗證的條件                                                                   | 驗證方式                                       |
| --------------------- | -------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------- |
| 「畫面不能當掉」      | 什麼叫當掉？   | ① 求解器對任何輸入都不拋出例外 ② 所有數值都是有限值 ③ 頁面文字不含 `NaN`／`Infinity` | 單元測試 + 1,000 個隨機電路 + E2E 檢查頁面文字 |
| 「立即重算」          | 多快才算立即？ | 200 個元件時，從按下 Enter 到下一幀繪製完成 < 100 ms                                 | 自動化效能量測，取 p95                         |
| 「學生看得懂的話」    | 主觀標準       | 每種錯誤有固定的一句中文說明，不出現「奇異矩陣」等術語；說明要包含「怎麼修正」       | 程式碼審查 + 測試檢查訊息存在                  |
| 「Undo 後與原本相同」 | 什麼叫相同？   | 電路資料**深度相等**，且求解結果**位元級相同**                                       | 60 步來回測試；E2E 比對整個 SVG 的 HTML        |
| 「標出有問題的元件」  | 標哪些？       | 回報的 `elementIds` 必須包含造成問題的元件；畫面上這些元件有紅色或橘色光暈           | 單元測試檢查 id；E2E 檢查光暈顏色              |

驗收標準本身已經把一部分需求改寫好了（例如「相對誤差小於 0.1%」）。但仍有不少描述需要開發者自己定義，例如「學生看得懂」。**定義清楚之後要寫進文件、讓客戶確認**，否則驗收時就會變成各說各話。

## 1.5 找出隱含的難題

把每條需求放在一起看，會發現有些需求單獨看很簡單，放在一起卻互相衝突。這個專案最大的隱藏難題是：

> **「電流計內阻為 0、電壓計內阻無限大」＋「自行實作 MNA」＋「任何接法都不可以當掉」**

- 內阻 0 代表電導無限大，直接寫進矩陣會出現除以 0。
- 內阻無限大代表電導為 0，可能讓某些節點和電路其他部分完全斷開，矩陣變成奇異。
- 學生一定會把電流計直接接在電池兩端（短路），而內阻為 0 的電池加上內阻為 0 的電流計，電流是 E / 0。

這三條需求結合起來，代表我們**不能只是「把元件寫進矩陣再解」**，必須先在系統分析階段想清楚每種理想元件該怎麼處理。第 2.7 節會詳細分析，第 6 章會看到解法。

其他在分析階段發現的隱含需求：

| 發現                                                                                    | 怎麼發現的                     | 處理                                       |
| --------------------------------------------------------------------------------------- | ------------------------------ | ------------------------------------------ |
| 兩個電動勢**相同**、內電阻為 0 的電池並聯，是國中課本的常見情境（電池並聯可以用比較久） | 想像老師的實際教學內容         | 不能當成錯誤，要能計算；電流平分給兩個電池 |
| 用電壓計量「斷開的開關兩端」是課本的標準實驗                                            | 列出電壓計的所有合法用法       | 「電壓計串聯」的判斷要排除這種情況         |
| 用電壓計直接量電池兩端（量電動勢）                                                      | 同上                           | 同上                                       |
| 已開啟 App 的分頁中貼上分享連結                                                         | **開發完成後**的驗收測試才發現 | 監聽 `hashchange`（第 8 章故事 6）         |

最後一列是個誠實的反省：需求分析不可能一次就完美，有些情境要等到測試階段才會浮現。這也是為什麼驗收測試不能省略。

## 本章重點

1. **背景故事比功能列表更重要**，它告訴你功能真正的用途。
2. 需求分成功能、非功能、限制、假設四類，各有不同的驗證方式。
3. 看到每條需求都要問：**「我要怎麼證明做到了？」**
4. 把需求放在一起看，才能找到隱藏的衝突（本案例是理想元件）。
5. 追溯矩陣讓需求、程式碼、測試互相對應。
