# 第 4 章　技術選型

> **本章目標**
>
> - 建立一套選擇技術的判斷標準
> - 了解每項技術在本專案中解決了什麼問題
> - 學會評估「要不要引入一個套件」
> - 認識版本相容性與供應鏈安全

## 4.1 選型原則

選技術時，很容易被「最新」「最多人用」「我最熟」左右。本專案用以下順序判斷：

1. **限制優先**：需求已經指定的（React 18 以上、TypeScript strict、Vite、Vitest），沒有討論空間。
2. **能不能不用？** 每多一個套件，就多一份學習成本、相容性風險和資安風險。能用語言或瀏覽器內建功能解決的，就不引入套件。
3. **成熟度**：維護是否活躍、文件是否完整、社群是否夠大。
4. **與既有工具的整合**：例如 Vitest 與 Vite 共用設定。

最後的結果是：**執行期只依賴 `react` 和 `react-dom` 兩個套件。**

## 4.2 技術清單與選擇理由

### 執行期

| 技術                     | 用途         | 為什麼選它                                                              | 考慮過的替代方案                            |
| ------------------------ | ------------ | ----------------------------------------------------------------------- | ------------------------------------------- |
| React 19                 | UI 框架      | 需求指定（18 以上）；宣告式 UI 適合「資料 → 畫面」的架構                | —                                           |
| TypeScript 6.0（strict） | 型別系統     | 需求指定 strict；判別聯合型別（discriminated union）很適合表達 7 種元件 | —                                           |
| SVG                      | 繪圖         | 見 ADR-5：DOM 事件、向量縮放、CSS 動畫、方便測試                        | Canvas、Konva（後者屬於需求禁止的繪圖套件） |
| `useReducer` + props     | 狀態管理     | 只有一份原始資料（`Circuit`），不需要全域狀態套件                       | Redux、Zustand：對這個規模來說太重          |
| `CompressionStream`      | 分享連結壓縮 | 瀏覽器內建，不需要套件                                                  | pako、lz-string                             |

### 開發與測試

| 技術                       | 用途               | 為什麼選它                                                             |
| -------------------------- | ------------------ | ---------------------------------------------------------------------- |
| Vite 8                     | 開發伺服器與建置   | 需求指定；啟動快、設定少                                               |
| Vitest 5                   | 單元測試           | 需求指定；與 Vite 共用設定與轉譯管線                                   |
| fast-check                 | 性質測試           | 支援固定種子（可重現），失敗時自動縮小反例（shrinking）                |
| Playwright                 | E2E 測試與效能量測 | 可以控制真實瀏覽器、執行頁面內的 `performance.now()`、處理下載與剪貼簿 |
| ESLint + typescript-eslint | 靜態檢查           | 需求要求 lint 無錯誤；`react-hooks` 規則可以抓到 hook 誤用             |
| Prettier                   | 格式化             | 格式交給工具決定，code review 時不必討論縮排                           |
| GitHub Actions + Pages     | CI／CD 與部署      | 與 repo 整合；靜態網站免費託管；部署前自動跑完所有檢查                 |

### 刻意不使用的

| 沒用的東西                         | 原因                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 線性代數套件（math.js、ml-matrix） | 需求禁止；而且自己實作高斯消去法只要 60 行                             |
| 電路模擬套件                       | 需求禁止                                                               |
| 狀態管理套件                       | 不需要                                                                 |
| CSS 框架（Tailwind 等）            | 介面簡單，一個 CSS 檔就夠                                              |
| 驗證套件（zod 等）                 | 驗證邏輯只有一個檔案，手寫的型別守衛就夠用，錯誤訊息也能完全用中文控制 |
| React 測試套件（Testing Library）  | 邏輯都在純函式中，用單元測試覆蓋；UI 用 Playwright 在真實瀏覽器中測    |

> **教學討論：什麼時候該引入套件？** 一個簡單的判斷方法是問三個問題：① 自己寫要多久？② 自己寫出錯的風險多高？③ 這個套件會帶來多少依賴？以驗證套件為例：自己寫只要 150 行，風險低（有完整測試），引入 zod 則會多一個依賴。反過來，fast-check 的 shrinking 功能自己寫很難做好，所以引入它是值得的。

## 4.3 TypeScript 嚴格設定的取捨

除了需求要求的 `strict: true`，本專案還開了一個很嚴格的選項：

```json
"noUncheckedIndexedAccess": true
```

開啟後，`array[i]` 的型別會變成 `T | undefined`，強迫你處理「索引超出範圍」的可能。代價是程式中會出現不少 `as number`：

```ts
// src/solver/linalg.ts
let pivotAbs = Math.abs(m[col * width + col] as number);
```

**這值得嗎？** 在 UI 程式中，這個選項常常只是增加雜訊。但在數值演算法中，索引錯誤會產生 `undefined`，再變成 `NaN`，而且不會報錯，只會讓結果默默出錯，而這正是需求 N1 最怕的情況。所以在這個專案中，選擇了更嚴格的設定。每個 `as number` 都代表「這裡我確認過索引在範圍內」。

## 4.4 版本相容性：一個真實的案例

開發第一天查詢套件的最新版本時，TypeScript 已經出到 **7.0**，但最後選用的是 **6.0.3**。原因是：

```text
typescript-eslint@8.72.0 的 peerDependencies：
  typescript: '>=4.8.4 <6.1.0'
```

typescript-eslint 還不支援 TypeScript 7。如果硬裝 7.0，lint 可能出現錯誤的結果，甚至無法執行。而「lint 無錯誤」是驗收標準之一。

這個案例的教訓：

1. **安裝前先查 peer dependencies**（`npm view <套件> peerDependencies`）。
2. **最新版不等於最適合的版本**。生態系中的工具需要時間跟上。
3. **把決定和原因寫下來**。本專案把它寫進了 `docs/architecture.md` 的工具表和 commit message。

## 4.5 供應鏈安全

專案完成後發生了一起資安事件，開發者把 Node.js 升級到最新版。這時要確認的不只是「程式還能不能跑」，還有依賴套件是否安全。驗收時做了以下檢查（詳見 [`docs/test-report.md`](../test-report.md)）：

| 檢查                 | 指令                     | 目的                                                   |
| -------------------- | ------------------------ | ------------------------------------------------------ |
| 依 lockfile 重新安裝 | `npm ci`                 | 確保安裝的版本和 lockfile 記錄的完全一致，不會偷偷升級 |
| 已知漏洞             | `npm audit`              | 比對漏洞資料庫                                         |
| 套件簽章             | `npm audit signatures`   | 確認套件確實是從官方 registry 發布、沒有被竄改         |
| 安裝腳本             | npm 11 的 `allowScripts` | 安裝腳本可以執行任意程式碼，是供應鏈攻擊的常見入口     |

最後一項出現了一個實際的判斷題：npm 擋下了 `fsevents` 的安裝腳本。要不要核准？分析之後發現：

- `fsevents` 是 Vite 在 macOS 上監看檔案用的選用套件。
- 套件裡已經附了預先編譯好的二進位檔。
- 被擋下的只是 npm 偵測到 `binding.gyp` 後自動加上的 `node-gyp rebuild`。

結論是**不影響功能，維持擋下**。這是最小權限原則的應用：不需要的權限就不給。

> **為什麼 lockfile 要 commit？** 沒有 lockfile 時，`npm install` 會依 `package.json` 的版本範圍（例如 `^19.3.1`）安裝當下最新的符合版本。兩個人在不同時間安裝，可能得到不同的程式碼。驗收標準要求「GitHub Repo 包含 lockfile」，就是為了確保任何人都能重現完全相同的環境。

## 4.6 用瀏覽器內建功能取代套件

專案中有幾個地方原本「直覺上需要套件」，最後都用內建功能解決：

| 需求           | 直覺的作法             | 實際作法                                    |
| -------------- | ---------------------- | ------------------------------------------- |
| 壓縮分享連結   | 引入 pako 或 lz-string | `CompressionStream('deflate-raw')`          |
| base64url 編碼 | 引入 base64 套件       | `btoa` 加上兩次字元替換                     |
| SVG 轉 PNG     | 引入 html2canvas       | `XMLSerializer` → `Image` → `canvas.toBlob` |
| 流動點動畫     | 引入動畫函式庫         | CSS `@keyframes` + `stroke-dashoffset`      |
| 下載檔案       | 引入 file-saver        | `URL.createObjectURL` + `<a download>`      |

現代瀏覽器的內建 API 已經非常完整。在引入套件之前，先查一下 MDN，常常會有意外的收穫。

## 本章重點

1. 選型順序：限制 → 能不能不用 → 成熟度 → 整合。
2. 每個依賴都有成本：學習、相容性、資安。本專案執行期只依賴 2 個套件。
3. 嚴格的型別設定在數值程式中特別有價值，因為它能擋下「默默變成 NaN」的錯誤。
4. 安裝前查 peer dependencies；最新版不一定最適合。
5. lockfile、`npm audit`、簽章驗證、安裝腳本管控，是供應鏈安全的基本功。

## 練習

1. **（評估）** 如果客戶改口允許使用線性代數套件，你會換掉自己寫的高斯消去法嗎？列出換與不換的理由。
2. **（調查）** 用 `npm view vite@8.3.5 dependencies` 和 `npm ls --all`，算出本專案的開發依賴總共引入了多少個套件。這個數字讓你有什麼想法？
3. **（實作）** 不用任何套件，寫一個函式把 `Uint8Array` 轉成十六進位字串。再寫一個測試驗證它。
4. **（判斷）** 某個套件的 README 說「安裝時需要執行 postinstall 腳本下載二進位檔」。在什麼情況下你會核准？在什麼情況下不會？
5. **（版本）** 查詢 typescript-eslint 目前的最新版本，看看它是否已經支援 TypeScript 7。如果支援了，升級需要做哪些檢查？
